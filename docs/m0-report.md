# M0 技術検証レポート

2026-11-10

M0 の目的は、設計の前提が成り立つかを実物で確かめることでした。3つの問いと答えは次のとおりです。

| 問い | 結果 |
|---|---|
| 同じコアが全ホストで同じ結果を出すか | 出る。ネイティブ、Node、workerd の Durable Object、Chrome の4ホストで状態ハッシュが一致 |
| Durable Object で 20TPS の tick ループが回るか | ローカルの workerd では回る。16人接続でも tick 落ちなし。本番環境は未計測 |
| WebGPU でチャンクを描けるか | 描ける。ソフトウェアラスタライザ上の Chrome 153 で描画と入力を確認。実 GPU での速度は未計測 |

## 1. 決定論

`sim::scenario` は「参加、移動、ブロック編集、保存、遠ざかる、戻ってストレージから再読込」を台本どおりに実行し、最終的なワールド状態とサーバーが送った全バイトをハッシュにまとめます。

| シード | tick数 | ネイティブ x86-64 | Node 22（WASM） | workerd DO（WASM） | Chrome 153（WASM） |
|---|---|---|---|---|---|
| 2026 | 600 | `28489699af34e2d8` | 一致 | 一致 | 一致 |
| -987654321 | 1500 | `acabac380d13744f` | 一致 | 一致 | 未実行 |
| -4962768465676381896 | 2000 | `99448d8804ccbb17` | 一致 | 一致 | 未実行 |

シード2026・600tickの台本では、ブロック変更2,174件、チャンク保存25件、再読込17件が発生します。

WASM の3ホストはいずれも V8 です。Firefox（SpiderMonkey）と Safari（JavaScriptCore）では未確認で、ゲーム内の `F8` で同じハッシュが出るかを確かめられます。

## 2. Java 互換の乱数

`tools/oracle/JdkVectors.java` が実際の JDK 21 から基準値を出力し、Rust のテストがそれと突き合わせます。

- `java.util.Random`: 9シード × 17系列（`nextInt`、境界付き `nextInt` 11種、`nextLong`、`nextFloat`、`nextDouble`、`nextBoolean`、混在呼び出し）で全一致
- Xoroshiro128++: JDK 自身の実装と状態遷移が5系列で一致

未検証: Xoroshiro の64ビットシードから128ビット状態への変換は公開資料に基づく実装で、ゲーム本体との照合は M2 で行います。`nextGaussian` は対数関数の移植が必要なため未実装です。

## 3. Durable Object の tick ループ

`tools/tick-probe.mjs` が WebSocket でスクリプト制御のプレイヤーを接続し、歩行とブロック編集を続けながら計測します。値はローカルの workerd（2 vCPU のサンドボックス）のものです。

| 条件 | クライアント実測TPS | 落ちたtick | タイマー間隔 p50 / p99 / 最大 | 読込チャンク | WASMメモリ |
|---|---|---|---|---|---|
| 8人、描画距離8、60秒 | 20.008〜20.013 | 0 | 52 / 61 / 69 ms | 2,567 | 19.1 MB |
| 16人、描画距離8、30秒 | 20.001〜20.005 | 0 | 53 / 66 / 71 ms | 5,100 | 36.1 MB |

- タイマーは平均52〜54msと遅れ気味に発火しますが、ペーサーが経過時間から必要なtick数を計算して追いつくため、平均は20TPSを保ちます。
- メモリは読込チャンクあたり約7.4KBでした。128MBの上限に対して、16人でも3割弱です。
- 通信量は移動し続けるプレイヤー1人あたり下り約57KiB/秒、チャンク1個は非圧縮で約5.6KBです。
- ネイティブでのtick処理時間は8人時に平均0.73ms、p99 6.1ms、最大12.8ms（参加直後のチャンク生成が集中する場面）でした。50msの枠に対して余裕があります。
- 17人目の接続は拒否されます（上限16）。
- ブロック編集後に開発サーバーを再起動しても、シード、時刻、編集内容が SQLite から復元されました。

## 4. クライアント

`tools/e2e.mjs` が実際の Chrome を操作し、29項目すべてが通りました。

- 入力: クリックでポインターロック、照準が真下のブロックを指す、左クリックで破壊、右クリックで設置、マウス200pxで視点が30.00度回転、`W` で視線方向に前進
- シングルプレイ: 121チャンクの受信とメッシュ化、描画、20TPS、ブロック設置、再読込後にシード・ブロック・時刻が OPFS から復元
- マルチプレイ: 同じ項目を Durable Object 相手に確認

配信サイズは gzip 後で server.wasm 47KiB、client.wasm 28KiB、JavaScript 約12KiB です。

## 5. 実際に見つけて直した問題

- workerd は新しい互換日付でバイナリフレームを Blob で渡すため、`binaryType = "arraybuffer"` の指定が必要でした。
- チャンク送信の予算が先着順だったため、8人同時だと後のプレイヤーの読込が遅れました。開始位置を毎tick回す方式に直し、8人の受信数が612〜635にそろいました。
- ヘッドレス Chrome はソフトウェア描画だとキャンバス表示の時点で WebGPU デバイスを失います。E2E は仮想ディスプレイ上のウィンドウ付き Chrome で実行します。

## 6. 当初案からの変更

| 当初案 | M0の実装 | 理由 |
|---|---|---|
| `apps/client` と `apps/edge` を分離 | `apps/web` に統合 | `cf` CLI の標準構成が、1つの Vite プロジェクトでクライアントと Worker を一緒に扱うため |
| Durable Object をバインディングで参照 | `ctx.exports.WorldDO` | 同一 Worker 内のクラスは型付きで直接参照できるため |
| wasm-bindgen | 生の C ABI、外部クレートなし | 受け渡すのはバイト列だけで足り、ビルドが軽く依存もゼロになるため |
| メッシュ生成はワーカープール | メインスレッドで1フレーム4msまで | M0の規模では十分。M1で移行 |
| Hono | 素の fetch ハンドラー | ルートが3本だけのため。API が増える M4 で導入 |

D1、R2、Turnstile、地形生成 Worker は M0 の範囲外で、未着手です。

## 7. まだ再現していないもの

M0 はエンジンの骨格で、ゲーム内容の再現はこれからです。

- 地形は仮の丘陵で、本来の地形生成とは無関係です（クラシックフラットのみ仕様どおり）。
- 移動は衝突なしの仮の飛行です。重力、慣性、当たり判定は M1 です。
- 光源計算、空、昼夜の明るさ、半透明ブロックはありません。
- ブロックは10種で、ID は独自です。

仕様どおりの部分: 20TPS、チャンク寸法と Y 範囲、セクション内の並び順、パレット圧縮の語長と詰め方、VarInt、面の明暗係数、AO の明るさ段階、視野角70度、マウス感度、座標系と向きの定義。

## 8. 残っているリスク

1. **本番の Durable Object での tick**: タイマーの精度、時刻の進み方、退避やデプロイ時の挙動はローカルと異なる可能性があります。デプロイ後に `tick-probe.mjs --edge https://…` で同じ計測ができます。
2. **実 GPU での描画速度**: ここでは計測できません。
3. **Chrome 以外のブラウザ**: 未確認です。
4. **耐久性の窓**: 編集は5秒ごとの自動保存で書き込みます。その間に Durable Object が退避されると最大5秒分が失われます。
5. **認証なし**: 公開するとだれでもワールドを作れます（README の注意を参照）。

## 9. この環境固有の事情

作業環境から `static.rust-lang.org` に接続できず、`rustup target add` が使えませんでした。代わりに Ubuntu の `rustc-1.97` と `libstd-rust-1.97-dev-wasm32` でビルドしています（`MC_CARGO=/usr/lib/rust-1.97/bin/cargo`）。通常の環境では README の手順どおりで動く想定ですが、rustup 版での WASM ビルドは未確認です（ネイティブのビルドとテストは rustup 版でも通っています）。
