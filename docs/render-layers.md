# 描画レイヤー・ブロック状態・部分形状（issue #16）

既存の状態 ID 0〜13（glass=11、oak_leaves=12、water=13）を保ち、
末尾にハーフブロックと草花の状態を追加した。
描画レイヤー、完全な遮蔽 `occludes`、衝突 `solid`、同種の面の省略 `cull_same`、
光の opacity / emission は独立した属性である。地形生成は変更しない。

Cube の面では、隣が occludes、または cull_same のブロックが同じ状態 ID に接するとき面を省略する。`oak_leaves` と `placed_oak_leaves`（状態 ID 51）の境界も両側の面を省略する。
Boxes は直方体の面がセル境界にある場合だけ同じ判定を使い、内部面は残す。
下付きハーフの上面、上付きハーフの下面は、隣が石でも消えない。
部分形状は occludes=false のため隣の面を隠さず、double のみ完全な遮蔽になる。
Cross は非表示判定をせず、×字2枚の表裏を4 quads として出力する。
これによりカットアウトの背面カリングを維持したまま、板の裏も描画できる。
ガラス・葉・水は同種の内面を省く（水の高さの差分は末尾参照）。葉2個が接する面は両側とも0面となる。
葉とガラス・空気の間の面は残り、石に接する葉側の面は従来どおり隠れる。石の面は透明素材によって隠れない。
森では木の追加により面数がほぼ倍増し、丸い樹冠1本の約360面中約250面が葉どうしの内面だったため、
`oak_leaves` に `cull_same = true` を指定した。cutout・opacity=1・tint・occludes=false・状態IDは維持する。
石に接するガラス側の面は隠れるため、石・ガラスが1個ずつ隣接する場合は石6面・ガラス5面。
石に完全に囲まれたガラスは0面になる。ガラスだけの例外は設けない。
AO と頂点周辺の光サンプリングの除外には occludes だけを使う。
セル境界の可視面では直外が必ず occludes=false なので、外側4セルの光採取は最低1サンプルを持つ。
内部面は AO=3（最大）とし、面の外側がある自セルの光をそのまま使う。
Cross も AO=3・自セルの光を使い、方向シェードは上面と同じ1.0とする。

頂点は2語のまま、位置と UV を1/16単位に変更した。ビットは下位から:

```text
word 0: x:9 | y:9 | z:9 | face:3 | ao:2
word 1: texture:12 | tint:1 | sky:4 | block:4 | u:5 | v:5 | water_top:1
```

位置はセクション内0〜256、UVは0〜16（復号時に16で割る）。
Boxes の各面は、箱のブロック内位置に対応した領域をテクスチャから切り取る。
例えば下付きハーフの側面はテクスチャ下半分になる。
4頂点（8語）を1 quad とし、
不透明→カットアウト→半透明の順に連結する。`mesh_section_layers` が3個の面数を返す。
WASM の `mesh_padded` / `client_mesh` は合計面数を返し、`client_mesh_ptr` が頂点先頭、
`client_mesh_count(0..2)` が直前の呼出しのレイヤー別面数を返す。空・無効入力では面数はすべて0。
Worker は頂点配列と面数を一緒に返す。メインのフォールバックも同じ ABI を使う。
共有インデックスは最大4096×54面を扱う。Cube と1箱の Boxes は各セル最大6面、
両面の Cross は4面、階段は最大18面、フェンスは柱と8本の横木で最大54面。
WGSL、`quadCenters`、半透明インデックスの並べ替えは同じ復号規則を使う。

描画順は空、不透明、カットアウトの後、カメラが雲面（Y=192）より下なら雲→半透明、
雲面と同じ高さか上なら半透明→雲とし、最後に選択枠を描く。
雲と半透明はどちらも深度を書かないため、水中から見上げる場合は雲を先に描き、
水面の色を通して雲が見えるようにする。雲面の高さは描画と順序判定で同じ定数を使う。
不透明とカットアウトは深度テスト・書込あり、カットアウトだけ alpha < 0.5 を discard。
半透明は深度テストあり・書込なしで、src-alpha / one-minus-src-alpha のブレンド。
不透明・カットアウトは背面をカリングする。半透明はカリングせず、水面を水中からも描く。
光マップ、方向シェード、AO、霧は3パスで共有する。
草・葉・水にはバイオームの色を乗算する。草ブロックの側面では、GPUテクスチャの
RGBに土の色、alphaに草の明るさを格納する。縮小時もそれぞれを平均してから
土の色に草の色を足すため、側面の草だけが上面と同じバイオーム色になる。

半透明セクションは毎フレーム、セクション中心からカメラまでの距離の遠い順に描く。
quad 中心は4頂点の平均から求める。カメラのブロック座標が変わったときとメッシュ更新時に、
近い可視セクションから quad を遠い順に並べ直す。
処理開始から1 msで次のセクションへの着手を止める。1セクションのソート・GPU転送は
不可分なので、その1個の処理だけ予算を超える場合がある。未処理のセクションは次フレームに回す。
不可視だったセクションも再び見えた時点で必要なソートを行う。
頂点を動かさず半透明用のインデックスだけを更新するため、AO の対角線と UV を保てる。
距離の同値は元の順を保つ。交差する半透明面の厳密な合成や order-independent transparency は扱わない。

ガラス・葉・草花の mip はRGBをalphaで重み付けして2×2平均する。alpha >= 0.5 を満たすピクセルの割合を、
次の解像度で表現できる最も近い面積に合わせる。平均 alpha の高い順に選び、
通過する値は最低160、非通過は最大96とする。同値は決定論的な順序。
最小 mip では1ピクセル未満の面積を表現できないため丸めがある。
水と既存の不透明テクスチャには通常の RGBA 平均を使う。
ブロックの模様は16×16のオリジナルのドット絵。鉱石は石と同じ地に鉱物の粒を重ねる。
配色、粒や葉の大きさ、透過部分の割合は統合版の実画像と比較して調整した。[Mojang Bedrock Samples v1.26.60.5](https://github.com/Mojang/bedrock-samples/releases/tag/v1.26.60.5)

土・粗い土・砂・雪は各面を、草・葉・砂岩は上下面を、ブロックの位置に応じて90度単位で回す。
原木の樹皮や砂岩の側面は上下を保つ。[統合版の面別定義](https://github.com/Mojang/bedrock-samples/blob/v1.26.60.5/resource_pack/blocks.json)

衝突は `solid` と `collision_boxes` を使い、1セルの複数の箱を列挙する。
クライアント予測とサーバー移動検証は共通の `physics::BlockWorld` を使う。
下付きハーフは高さ0.5、上付きは0.5〜1、double は1。段差0.6で下付きに上がれる。
水・草花は衝突せず、ガラス・葉は衝突する。未読込チャンクは移動上の壁になる。

レイキャストは `selection_boxes` に交差させ、空の半分を通り抜ける。
草花の選択箱は x/z=5/16〜11/16、y=0〜10/16。水は選択を通過する。
当たった面と自セル内の Y（0〜1、上端は1）、選択箱の min/max を返す。
WASM 出力は x/y/z/face と箱の min/max が十個の i32 LE、その後に Y が f64 LE。
選択枠はその箱を0.002ずつ膨らませる。選択箱は草花の板の全体とは一致しない。
水流・浮力・泳ぎは扱わない。

Rust で面数、境界、AO・光採取、光の減衰、クライアントとサーバーの衝突・設置を検証。
`pnpm test:host` でセクション・quad の順序、レイヤー境界、WASM の面数とミップを検証する。
`tools/e2e.mjs` はガラスの奥・水の下の地形の素材を変更して画素が追従すること、
ガラスの透明部が地形の色を保つこと、水の色が描画されることとページエラーを確認する。
E2E はレビュー側で実行する。

決定論の既存台本は登録総数を乱数の範囲に使っていたため、そのままでは ID 追加だけで
編集対象と乱数列が変わる。`sim::scenario` の選択範囲を従来の air..=lamp_block に固定し、
seed=2026 / 600 ticks の既存ハッシュ `88d6e0e1abd58ec4` を Rust テストでも固定した。
新しい素材は別の素材・衝突・光・ABI テストで扱う。


## 状態とモデル

`BlockState` は保存・通信とも従来どおり u16。ブロックは連続した状態範囲を持ち、
先頭の状態がインベントリの既定値。`info(state)` は状態の描画・衝突・光情報を返す。
`block` / `properties` / `state_name` / `parse_state` でブロックと性質を相互変換する。

| ブロック | 状態 ID | モデル |
|---|---|---|
| 既存ブロック（air〜water） | 0〜13を維持 | Cube |
| oak_slab | 14 bottom、15 top、16 double | Boxes、Boxes、Cube |
| cobblestone_slab | 17 bottom、18 top、19 double | Boxes、Boxes、Cube |
| red_flower / yellow_flower / short_grass | 20 / 21 / 22 | Cross |

`Box16` の座標は0〜16。下付きは y=0〜8、上付きは8〜16。
ハーフは板材・丸石のテクスチャを使い、草花3種は輪郭に沿って切り抜いたドット絵を使う。
草はグレースケールに草色を乗算する。
`client_block_registry` は状態名、ブロック既定値・状態数、モデル、遮蔽、各面のテクスチャ名とアイコン用の箱を
JSON配列（添字が状態 ID）で返す。UI 側に状態 ID の対応表を重複して持たせない。
F3 の Target 行は `oak_slab[type=top]` のような状態文字列を表示する。

## 置き方とブロック一覧

クライアントの `placementState` はレイキャストの面と自セル内 Y を使う。
上面に置くハーフは bottom、下面なら top。側面は Y < 0.5 なら bottom、以上なら top。
同じブロックの下付きの上面、上付きの下面を狙えば、そのセルを double にする。
隣接する設置先も、同じ種類のハーフの空いた半分に対応する場合だけ double にできる。
それ以外の置き換え先は空気・水だけ。未読込や別種のハーフ、double、草花への上書きはしない。
草花・草は設置先の直下が `occludes=true` のときだけ置ける。下の支えが後から壊れても、
残った草花を除去する処理はない。体と重なる設置や、そこから抜ける既存の扱いは保つ。

E でブロック単位の一覧を開き、クリックで現在のホットバー枠を入れ替える。
E / Esc / 閉じるボタンで閉じる。開くと入力をクリアしてポインターロックを解除し、
閉じると再ロックを試みる。ブラウザーが拒否した場合は一時停止画面をクリックして再開できる。
E はキー設定でも予約し、古い保存設定に E の割当があれば既定設定に戻す。
中クリックは状態ではなくブロックの先頭状態を拾い、既存の枠を選ぶか現在の枠を入れ替える。
重複するホットバー枠は許可し、選択は状態 ID ではなく枠番号で管理する。

既定の9枠は stone / dirt / oak_planks / oak_slab / oak_log / glass / oak_leaves / water / lamp_block。
`cf-minecraft.hotbar.v1` に9個のブロック名を保存し、次回も先頭状態として復元する。
localStorage 自体へのアクセス・読書きは try/catch。壊れたデータ、不明な名前、空気、
枠数不正は既定に戻し、保存失敗時はそのセッション内で選択を維持する。

## サーバーの検証と決定論

サーバーは従来の参加・読込・範囲・距離検証に加えて、有効な状態 ID と、草花の直下の
`occludes` を検証する。置き換え制限はクライアント UI だけで行い、サーバーでは任意の
既存状態への上書きを許す。決定論の台本が同じセルを直接上書きする既存挙動を保つためである。
台本の地形生成・乱数の状態範囲は変更せず、native と Node の seed=2026 / 600 ticks は
`88d6e0e1abd58ec4` のまま。サーバーはハーフの向きを推測せず、受信した状態を適用する。

## 水面と本家との差

水には上下面の波紋と側面を下る流れの2組のドット絵を使う。各32コマを縮小画像とともにGPUに転送し、
描画時に上下面は2ティック、側面は1ティックごとに次のコマに切り替える。[統合版のアニメーション定義](https://github.com/Mojang/bedrock-samples/blob/v1.26.60.5/resource_pack/textures/flipbook_textures.json)

水セルの上が水でなければ、上面と側面の上端の頂点に `water_top` を付ける。
WGSL でその Y を1/9ブロック下げ、セル内8/9の高さにする。整数の1/16座標を丸めない。
上が水なら下げず、積み重なった水の側面は連続する。半透明の中心計算も同じ補正を使う。
隣が水の側面は、自分が高さ1で隣が8/9のときだけ、8/9〜1の帯を出す。
同じ高さ、または自分のほうが低い場合は出さず、境目の帯は高い側だけが所有する。
帯の上下端はどちらも整数位置 y=16 とし、下端だけ `water_top` で1/9下げる。
側面の UV の V にもフラグの1/9を加え、帯はテクスチャの V=0〜1/9を切り取る。
通常の水側面の上端もこの補正で V=1/9となり、同じ高さでUVが一致する。
上面のUVは下げない。頂点の語数・フィールドと半透明の中心計算は変更しない。
高さ判定に必要な側面隣接セルの上は `(x±1,y+1,z)` または `(x,y+1,z±1)`。
中心セルの y は0〜15なので、セクション境でも1セル外周の18³パディング内（-1〜16）で取得できる。
上のセルを推測するフォールバックは不要で、隣接セクションの実際の状態を使う。
これは源の水の高さだけを表し、流れによる高さ・隣接水からの勾配はない。

本家の方向別の光遮蔽や部分面の覆い合いは扱わない。上下のハーフ同士が接しても
相手の一部の面を切り取って隠す処理はなく、double のみ完全な遮蔽になる。
内部面・Cross の光は自セルの値、AO は最大とする簡略化である。
光の減衰の詳細は [lighting.md](lighting.md) を参照。

Rust は形状の座標・UV・面数・両面・水面、状態変換、段差・頭上の空間・草花通過、
サーバーとクライアントの経路、レイ交差・面・Y、設置の拒否と double を検証する。
host テストは置き方の境界、WASM レジストリ、ホットバー保存と破損、E の予約、
頂点復号・半透明の並べ替えを扱う。
E2E には下付きハーフの設置・歩いて上がる・double 化、草花の画素と通過、E/Esc、
一覧からの選択、再読込後の保存、中クリック、ページエラーの検査を含む。
さらに階段の yaw に従う設置と歩行上昇、直角に置いた階段の選択箱の変化、フェンスへのジャンプを追加する。
角の検査には `window.__mc.raycast(origin, direction, max)` が返す選択箱と交点 Y を使い、
元の階段の状態 ID を変えずに形が変わることを確かめる。E2E は追加・構文確認までとし、実行はレビュー側で行う。

## 階段・フェンスの隣接形状

公開規則の出典は [Minecraft Wiki: Stairs — Placement](https://minecraft.wiki/w/Stairs#Placement)
と [Fence — Barrier](https://minecraft.wiki/w/Fence#Barrier)。逆コンパイルしたコードは使用しない。

既存の状態 ID 0〜22 を保持し、oak_stairs=23〜30、cobblestone_stairs=31〜38、oak_fence=39 を追加する。
階段の順序は north/south/west/east × bottom/top（上下が先に変化）。facing は高い段の側を指す。
本家は shape や各方向の接続を状態に持つが、ここでは階段の facing/half だけとフェンス1状態を保存する。
`shape_boxes` が隣の保存状態からその都度形を計算するため、隣の編集で自身の状態 ID は変えない。
クライアント予測、サーバー移動検証、メッシャー、レイキャストで同じ計算を使う。

置き方はプレイヤーの水平 yaw（度）から facing を決め、高い段が奥になる。
yaw は360度で折り返し、正規化後は次の対応とする。境界は yaw が増える側の方角に含める。

| yaw の範囲 | facing | 高い段の方向 |
| --- | --- | --- |
| 315以上360未満、0以上45未満 | south | +Z |
| 45以上135未満 | west | -X |
| 135以上225未満 | north | -Z |
| 225以上315未満 | east | +X |

上下はハーフブロックと共通で、下面に当てたら top、上面なら bottom。
側面なら交点のセル内 Y が0.5以上で top、それ未満で bottom（負のワールド Y でも同じ）。
階段もフェンスも設置先が空気・水のときだけ置ける。階段は重ねて double にせず、フェンスは向きや上下を持たない1状態。
選択画面とホットバーでは、上・南・東の面を描いた立体アイコンで段差や素材を見分けられる。
フェンスのアイコンは2本の支柱を横木でつないだ形で、草花は正面から描く。
既定のホットバーは変更しない。

階段は half の側の厚さ8/16の板と、残りの高さの段を組み合わせる。
衝突・選択には描画と同じ箱を使い、全高1ブロック、段差0.5ブロックなので物理の段差上限0.6で歩いて上がれる。
facing の前の階段が同じ half かつ直交方向を向くと、両方向の半分の共通部分を段にする（outer、1/4）。
ただしその隣の向きと逆側に自身と同じ facing/half の階段がある場合は outer にしない。
outer が成立しない場合、後ろの階段が同じ half かつ直交方向を向くと、その向きの欠けた1/4を追加する（inner、3/4）。
その隣の向きの側に自身と同じ facing/half の階段がある場合は inner にしない。
左右は隣の facing で決まり、材質は問わない。top は同じ平面形状で上下を反転する。

フェンスは x/z=6〜10/16 の柱を持ち、同じ高さの四方にフェンスまたは occludes があれば接続する。
本家の全接続対象は再現せず、この2条件に限定する。描画の腕は幅2/16、y=6〜9/16 と12〜15/16。
選択は腕の縦の隙間も含む高さ1の箱、衝突は柱と腕の高さを1.5に延ばす。
衝突探索はセルの下へ1セル広げ、足が上のセルにあってもフェンスを検出する。
サーバーの段差経路は足元の支持を確認してから試し、足場のない空中で追加の上昇を許さない。
階段とフェンスはともに solid=true、occludes=false、opacity=0。既存のテクスチャを使う。

形の計算は上下のセルや隣の計算済み形状を参照せず、同じ高さの直近4セルだけを見る。
そのためメッシャーの18³のパディングと、編集時の周囲1セルのセクション再構築で足りる。
箱同士の内部面は従来の Boxes と同様に残し、セル境界の面だけ隣の occludes で省略する。

Terrainの草・葉・水は256×256×3層の色の地図（1セル4ブロック）を共有し、更新したチャンクの4×4矩形を3層まとめて1回GPUへ転送する（リセット時も全3層を1回）。
色の更新予算は前フレームからの経過時間の8%とし、1〜10msに制限する（60fpsで約1.3ms、8fpsで10ms）。
共通の頂点シェーダーで斜め4点のレベル0サンプルを平均し、補間した色を不透明・カットアウト・半透明の各パスに渡す。
Flat / DebugHillsとジェネレーター未確定時の地図は既定の草・葉・水の色を使う。
草と葉のアイコンは統合版の所持時の色に合わせて着色する。[統合版のテクスチャ対応表](https://github.com/Mojang/bedrock-samples/blob/v1.26.60.5/resource_pack/textures/terrain_texture.json)

## 見える範囲のカリング

各 16×16×16 セクションの `!blocks::occludes(state)` のセルを flood fill し、
各連結成分が触れる境界面の全ペアを 15 ビットで記録する。ガラス・葉・水・
部分形状も通り抜けられる扱いとなる。作業配列は再利用し、計算結果はクライアントの
BTreeMap にキャッシュする。チャンク受信・破棄ではそのチャンク、ブロック変更では
変更したセクションだけを無効化する。光によるメッシュ更新はこのキャッシュを無効化しない。

カメラのセクションから BFS で探索する。始点は全方向へ進める。その先では入口面と
出口面が連結している場合だけ進み、同じセクションへの別の入口も考慮する。
進む軸でカメラからの距離が増える方向だけに進む（戻り防止）。横は描画距離の正方形、
縦は 0..24 に制限する。未受信のチャンクは全ペア接続として先へ進む。
カメラがワールドの縦範囲外にいる場合は全セクションを可視とする。
カメラのセクションまたは接続情報が変わったときだけ、フレームごとに最大一度更新する。
可視集合が変わったときだけ、WASM 出力バッファで `cx,sy,cz` を JS に渡す。

メッシュ待ち行列は可視セクションから距離順に取り出す。隠れたセクションは dirty のまま
後回しになり、見えるようになった時点で作成する。`meshQueue` は可視の待ち行列と
実行・アップロード待ちの仕事、`hiddenDirty` は隠れた dirty セクションを表す。
不透明・カットアウト・半透明の全パスで同じ集合と視錐台判定を使い、半透明の並べ替えも
可視メッシュだけで行う。F3 と `window.__mc.stats().visibleSections` は読み込み済み
セクションのうち可視の数（空のセクションも含む）、`stats().sections` は読み込み済み
チャンク数 × 24 を表す。

URL の `cull=0` で探索によるカリングを停止し、全セクションをメッシュ化・描画対象にする。
比較や問題発生時の回避に使える（視錐台判定は引き続き適用する）。

面単位の接続は境界面上の穴の位置を区別しないので、余分なセクションが見えることがある。
戻り防止で折り返す経路を省くため、まれに本来見える区画がカメラの移動まで見えなくなる
場合がある。可視になった区画のメッシュ作成は非同期なので表示が 1 フレーム以上遅れる
場合もある。地形生成・保存形式・光の計算には影響しない。

## たいまつ（⑦-4b）

`torch`（状態77）は幅2/16、高さ10/16の中央に立つ棒。`wall_torch`（状態78〜81）は
north、south、west、east の順で、壁から離れる向きに傾く。どちらも上端2/16に炎の色を描く
cutout モデルで、照準には棒を囲む箱を使い、プレイヤーとの衝突はない。
ブロック用とアイテム用にそれぞれ16×16のピクセル絵を使う。

上面に右クリックで床用、横の面に右クリックで壁用を置く。付ける面はセル境界で
全面が固体である必要があり、下面には置けない。支えの面が失われるとたいまつも壊れ、
サバイバルでは1本落とす。水と溶岩はたいまつのセルへ流れ込まない。

チャンクのパレットと保存形式は従来どおりで、既存の状態 ID を保持する。
接続プロトコルは22。双方のレジストリが追加状態を扱えることを接続時に確認する。

プロトコル23の変更は矢の発射情報を追加する。[矢の同期形式](entities.md)

プロトコル 24 では、発言・参加・退出をチャットパケットで同期する。詳細は [チャット](chat.md) を参照。

プロトコル 25 では、ゾンビの近接攻撃による押し返しと Mob の燃焼状態を同期する。詳細は [押し返しと燃えている見た目](mobs.md#プロトコル-25) を参照。
