# プレイヤー物理

`crates/physics` は I/O やワールド生成に依存しない20TPSの予測用物理。
サーバー側の移動検証にも同じ衝突解決を利用する。
逆コンパイルしたソースコードは使わず、下記の公開仕様と issue #13 の指定式から実装した。
通常ブロック上での移動、飛行、水源と流れる水での泳ぎを扱う。
バージョンごとの追加属性、特殊な摩擦、姿勢による体積変更、エンティティ同士の衝突は対象外。

## 座標と数値

- 位置・速度・AABB は `f64`。位置は足元の中心、速度はブロック/tick。
- 立位の幅 `0.6f`、高さ `1.8f`、段差 `0.6f` は Java float 相当の `f32` から `f64` に拡張。
  目の高さは1.62。スニーク中もこの PR の当たり判定は立位のまま。
- yaw は `f32` の度数。0度は +Z、90度は -X。右入力は正。
  `yaw * (PI_f32 / 180f)` を `jmath::sin_table::{sin, cos}` に渡す。
- 入力、加速、水平摩擦、正規化は `f32`。算出した加速を `f64` の速度へ加算。
  重力は `0.08_f64`、鉛直抗力は `0.98_f32 as f64`、飛行鉛直抗力は `0.6_f64`。
  平方根は IEEE 754 の `sqrt` を使用し、libm の三角関数・HashMap・FMA は使用しない。

## 1 tick の式と順序

1. 各軸で絶対値0.003未満の速度を0にする。
2. 接地中にジャンプ入力があれば `vy = 0.42f`。ダッシュジャンプは
   `vx -= sin(yaw) * 0.2f`、`vz += cos(yaw) * 0.2f`。
   長押し時の再ジャンプ間隔は10 tick、離すと待ち時間を解除する。
3. 前後・左右の入力をそれぞれ [-1, 1] に制限し、歩行スニーク中は0.3倍、常に0.98倍する。
   長さが1を超える場合は正規化する。そのため斜めは直進の最大1/0.98倍になる。
4. 地上の水平摩擦 `q = 0.6f * 0.91f`、空中は `q = 0.91f`。
   地上の加速 `a = movement_speed * (0.16277136f / (q*q*q))`。
   `movement_speed` は歩行0.1f、ダッシュは `f32(0.1_f64 * 1.3)`。
   空中は0.02f、ダッシュ中は0.026f。スニーク中の歩行ではダッシュを解除する。
5. 加速済み入力を `s`（右）、`f`（前）とすると、
   `vx += -s*cos(yaw) - f*sin(yaw)`、`vz += f*cos(yaw) - s*sin(yaw)`。
6. スニーク接地中は足元から0.6下げたAABBに支持があるか調べる。
   X、Z、XZの順に、支持がなくなる移動量を0.05ずつ0へ近づける。
7. 速度分の移動を **Y → X → Z** の順にブロックAABBで切り詰める。
   移動前後を覆う領域を走査するので、1 tickでブロック幅以上を進んでも壁を抜けない。
   接触面だけの一致は重なりとみなさず、阻止された軸の速度を0にする。
8. 地上または着地する移動が水平に阻止された場合、0.6上昇、X/Z移動、下降の別経路を試す。
   天井で上昇量を制限し、水平距離が元の経路を超える場合だけ採用する。
   下降が阻止されたとき接地とする。1.0の段差はジャンプなしでは上れない。
9. 移動後に `vx *= q`、`vz *= q`、`vy = (vy - 0.08) * 0.98f`。

地上の直進加速はおよそ0.098で、終端での移動距離は `0.098 / (1-q)`、
およそ0.21585ブロック/tick = 4.317 m/s（ダッシュ5.612 m/s）。
保存される速度は移動後の抗力適用済みなので、これより小さい。
ジャンプの最高到達点はおよそ1.2522。

## 水中の移動

tick の開始時に足元から 0.4 ブロック上の点を調べ、そのブロックが水源か流れる水なら `Player::in_water` を立てる。飛行中は飛行の式を優先する。泳ぎでは接地時も空中の水平加速を使い、ジャンプ入力中はクールダウンなしで `vy += 0.04`。移動後は全軸を 0.8 倍してから `vy -= 0.02` とする。ジャンプ入力中に壁で水平移動を阻まれ、移動後の AABB を 0.6 ブロック上げた位置が空いていれば、最後に `vy = 0.3` として岸へ上がる。接地、段差、スニークの衝突処理は共通。[水とバケツ](water.md#泳ぎ)

## クリエイティブ飛行とクライアント

飛行中は重力を使わず、水平加速は0.05f（ダッシュ0.1f）、水平抗力0.91f。
ジャンプ/下降入力に対して `vy += direction * 0.05f * 3f`、移動後に `vy *= 0.6`。
直進の終端速度はおよそ10.889 m/s（ダッシュ21.778 m/s）、鉛直は7.5 m/s。
飛行中も同じAABB衝突を使う。飛行中にスニークを押すと下降し、端の保護は使わない。

開始時は飛行で速度0。ジャンプの押し始め2回が7シミュレーションtick以内なら飛行を切り替える。
ブラウザのキーリピートは数えず、短い押下も次のtickへ保持する。
体がブロックと重なる場合・未受信チャンク内では歩行への切り替えを拒否し、飛行を維持する。
この PR では着地による自動飛行解除をせず、明示的な切り替えのみとする。
未受信チャンクは固体として扱う。現行ブロックレジストリは空気以外すべて完全な立方体である。
トレイトはブロック内に収まる任意の単一AABBを返せるため、0.5段差もテストできる。

WASM ABI はリセット、飛行切り替え、1 tick更新の3関数。
更新結果は足元xyz・速度xyz（6個のf64 LE）、接地・飛行（2個のu8）。
ブラウザは50msごとに物理を進め、前回と今回の足元座標を残余時間/50msで線形補間して描画する。
カメラだけ目の高さを加える。物理のtickを進めるたび（20TPS、50ms分の物理ごと）に、
そのtickの衝突解決済みの足元を直ちに報告する。1フレームで2tick進む場合も、各tickの後に
1回ずつ順番に送り、最後の位置だけにまとめたり、別の50msタイマーで間引いたりしない。
複数tickの端点だけでは、角を下りながら横へ抜ける経路を単一のY→X→Z掃引で再現できないためである。
停止中もtickごとに報告する。ブロック編集前や再接続時の追加報告は維持する。
描画用に補間したカメラの位置は送らない。両端が安全でも補間点はブロックの角に重なる場合がある。
既存のフレーム時間上限100msを維持し、バックグラウンド復帰時に大量の追いつき更新を行わない。
autopilotは従来の軌道計算を維持。`window.__mc.setCamera` は速度と補間履歴もリセットする。

f32演算の各段階をbinary32へ丸め、8 tick目にジャンプ、24 tick目からダッシュ、28 tick目にダッシュジャンプする。

斜め入力、ダッシュ、上昇/下降、入力を離した後の慣性も両ホストで照合する。

## サーバー側の移動検証

統合サーバーと Durable Object は同じ `sim` / `physics` を使う。
接続時の足元は通常スポーン位置とし、最後に受理した位置と tick をクライアントごとに保持する。
通常の PlayerPos は有限値と世界境界（各座標の絶対値29,999,984未満）を確認する。

水平距離（XZ のユークリッド距離）と鉛直距離（Y の絶対値）に独立した予算を持つ。
サーバーの経過 tick ごとに水平1.5、鉛直4.5ブロックを補充し、最大40 tick（2秒）分、
水平60・鉛直180まで貯める。接続時にもこの予備を与え、まとめて届く複数パケットは
同じ予算を順に消費する。同じ tick のパケット数や拒否回数では補充しない。
飛行ダッシュの終端は `0.98 * 0.1 / (1 - 0.91) ≈ 1.089`、
落下の終端は `0.08 * 0.98 / (1 - 0.98) ≈ 3.92` ブロック/tick。
この値より大きい定数と予備で、数値の丸め・送信間隔のゆらぎを許容する。
これは入力を再現する検証ではなく、短いバーストを許す移動量の上限である。

幅0.6・高さ1.8の AABB で、共有の `physics::resolve` を使って検証する。
移動元のAABBに既に重なっている既知の固体は、その報告の掃引と移動先の重なり判定の両方から除く。
自分や他プレイヤーが体に置いたブロックから、小刻みな移動でも脱出できるようにするためである。
例外は報告ごとに移動元から計算し直すため、脱出後の再侵入や、新しい別の固体への侵入は拒否する。
それ以外の固体に移動先のAABBが重なる場合は拒否する。未ロードチャンクはこの例外に含めない。
掃引はクライアントと同じく **Y全体 → X全体 → Z全体** の順とし、各軸の中だけで最大1ブロックに刻む。
全軸を同率で刻むと、落下後に横へ進む実際の経路を再現できないためである。
要求した移動と解決結果がいずれかの軸で0.1以上ずれた場合は拒否する。
各軸の刻みごとのずれは次の刻みに持ち越す。予算の上限と各軸の刻みにより走査範囲を有限に保ち、薄い壁も飛び越えない。

通常の Y→X→Z 経路が通らない場合は、上へ最大0.6→X→Z→下降の段差経路も試す。
上昇は天井で制限し、要求された上り幅がその高さを超える場合は拒否する。
上昇後・水平移動後・下降後の空間を共有の `physics::resolve` と AABB の重なりで検査し、
移動量の予算、元の重なりからの脱出、未受信チャンクを固体とする規則も適用する。

クライアントの物理は開始時の接地、または下向き速度と通常経路の Y の衝突を条件に段差経路を試す。
サーバーは速度を知らず、端点からの接地・着地の推測は正常な予測を拒否するため、そのガードや下向き probe は設けない。
落下中に角を回ってハーフに着地すると、通常経路の Y より報告された落下量が短くなり、
開始位置によっては最終 Y が増えることもある。空間として通れる経路ならこれらも受理する。
途中の報告を省いた角の下りも、段差経路が空いていれば受理する。
各 tick の報告を複数パケットのまま同じサーバー tick に受け取る場合は、従来どおり順に検証する。

残る甘さとして、改造クライアントは空中でも最大0.6の段差上昇を利用でき、
ジャンプの頂点から高さ1.5のフェンスを越える報告も空間が空いていれば受理される。
通常のクライアント物理はフェンスの高さ1.5の衝突箱に阻まれ、ジャンプしても越えられない。
クリエイティブ相当の現段階ではこの差を許容する。将来はサーバーも速度を追跡し、
実際に段差経路を使える状態かを検証する必要がある。

サーバーで未ロードのチャンクは固体とし、移動パケットを理由とした生成・同期ロードは行わない。
保存済みチャンクの読込待ちも同じ扱いになる。クライアントも未受信チャンクを固体として扱う。
接地は必須にしないため、予測で置いたブロックがサーバーに拒否され、その上に登っていた場合も、
空中の正常な位置として許容する。既存の固体を予測で壊した場合は、サーバーで破壊が受理されるまで
固体のままであり、通過には訂正が発生する。

拒否時は位置と消費済み予算を保持し、`positions_rejected` を増やす。
最後に受理した足元を PlayerCorrect で返すが、送信はクライアントごと・tickごとに1回まで。
クライアントは物理位置を戻し、速度を0にして描画補間を飛ばす。
訂正回数は `window.__mc.stats().positionsCorrected` で確認できる。
プロトコルは版2であり、旧版の Hello は参加を許可しない。

Teleport は通常の移動検証を通らず、有限値と世界境界だけを確認し、移動の基準と予算をリセットする。
許可はホストが接続時に指定し、パケットから取得しない。Durable Object は信頼するルーターが渡す
`X-MC-User` が `ops:` または `dev:` で始まる接続だけ、統合サーバーは
`import.meta.env.DEV` のビルドだけ許可する。ログインした通常ユーザーには許可しない。
`__mc.setCamera` と tick-probe の初期配置は Teleport を使う。
autopilot はローカルのカメラだけを周回させ、PlayerPos を送信しない。
保存・再読込を検証する決定論シナリオも、自分で置いた固体を横切る台本のため
ホスト許可の Teleport を使う。通常移動の軌跡は別の sim テストで検証する。

### 再接続時の位置

ホストは `connect_at` に初期位置を渡せる。未指定・非有限値・世界境界外の値はスポーンに戻す。
`client_position` はキュー中や拒否された位置を含めず、最後に受理した足元だけを返す。
Durable Object は各接続の終了時（同一ユーザーの接続置換、管理側の切断も含む）にこの位置を
ユーザーIDごとのメモリに記録し、同じユーザーの再接続で初期位置として渡す。
別ユーザーには引き継がず、通常ユーザーに Teleport 権限を与えることもない。
位置は永続化しないため、DO の eviction・再作成（debug evict を含む）後はスポーンが基準となる。
クライアントは初回 Welcome では従来のスポーン表示を使い、再接続の Welcome ではカメラを保つ。
サーバーの位置と異なる場合は、その後の PlayerCorrect に従い、速度と補間をリセットする。

### ネイティブの移動ベンチマーク

`native-server bench` はホスト指定の初期位置でプレイヤーを分散し、許可済み Teleport で
毎tick 0.28ブロック進める。地形の衝突や未ロードチャンクを待たずに、チャンクの生成・配信・
アンロードの負荷を測る台本である。通常の移動検証の正しさは sim の物理軌跡テストで検証する。
結果の `positions_rejected` を出力し、0であることも検査する。

プロトコル 24 では、発言・参加・退出をチャットパケットで同期する。詳細は [チャット](chat.md) を参照。

プロトコル 25 では、ゾンビの近接攻撃による押し返しと Mob の燃焼状態を同期する。詳細は [押し返しと燃えている見た目](mobs.md#プロトコル-25) を参照。
