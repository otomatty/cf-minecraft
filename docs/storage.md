# チャンクの圧縮保存

シングルプレイの OPFS と Durable Object の SQLite BLOB に使う形式です。形式と圧縮と書き込み計画は `crates/storage` が決めます。このクレートは I/O を行いません。HashMap と浮動小数点の超越関数は使いません。`meta.json` の形式と保存処理は変えません。

## ファイルと位置表

ファイル名は `r.<rx>.<rz>` です。1ファイルに32×32チャンクを入れます。`rx = floor(cx / 32)`、`rz = floor(cz / 32)` です。位置表の番号は `cz.rem_euclid(32) * 32 + cx.rem_euclid(32)` です。例えばチャンク `(-1, -33)` は `r.-1.-2` の番号1023です。

整数はすべてリトルエンディアンです。セクタは4096バイトです。先頭49152バイトを位置表に使います。1024個の項目があり、各項目は24バイトのスロットを2個持ちます。位置は `番号 * 48 + スロット番号 * 24` です。この初版では別のマジック値やファイルヘッダーを持ちません。

| スロット内の位置 | 内容 |
| --- | --- |
| 0 | 世代番号 u64。0は未使用です。 |
| 8 | データの開始セクタ番号 u32。12以上です。 |
| 12 | データのセクタ数 u32。0以外です。 |
| 16 | 先頭16バイトの CRC-32/IEEE u32です。 |
| 20 | CRC のビット反転値 u32です。 |

チェックサムと反転値を検証します。データがファイルの範囲に収まることも確認します。有効なスロットのうち、世代番号が大きい方を読みます。同じ世代なら後ろのスロットを選びます。通常の書き込みでは世代は重複しません。世代番号が上限に達した場合は書き込みを拒否します。

無効なスロットは無視します。両方とも無効なら未保存です。初回保存中の強制終了もこの扱いです。既存データの更新では、更新しない方の有効なスロットが残ります。短いファイルの位置表の不足部分は、ホストがゼロで補います。

データは次の順に並べます。圧縮データの後ろはセクタ境界までゼロで埋めます。

| 位置 | 内容 |
| --- | --- |
| 0 | 圧縮データのバイト数 u32です。 |
| 4 | 圧縮方式 u8です。1は zlib です。 |
| 5 | 展開後データの CRC-32/IEEE u32です。 |
| 9 | 圧縮データです。 |

圧縮は純 Rust の `miniz_oxide 0.8.9` の zlib、レベル6を使います。バージョンを固定します。SIMD 機能は有効にしません。ネイティブと WASM の書き込み計画全体を比較します。圧縮バイト列も一致します。展開後は CRC も確認します。1チャンクの展開後サイズは16 MiBまでです。リージョンの末尾は u32 のバイト位置の範囲に制限します。

## 書き込みと強制終了

Rust は順序付きの2個の書き込みを返します。各書き込みは位置とバイト列を持ちます。ホストは各書き込みの直後に flush します。

1. 両方の有効なスロットが参照する範囲を使用中とします。位置表の12セクタも保護します。
2. 最初に見つかる連続した空き範囲を選びます。空きが足りなければ末尾を使います。
3. 新しいデータを全量書いて flush します。
4. 現在選ばれていない方のスロットを、次の世代番号で書き換えます。初回は先頭のスロットです。
5. そのスロットを全量書いて flush します。この時点で保存完了です。

データの flush 前後に落ちても、以前の位置表とデータは変わりません。位置表の flush 前に新しい項目が永続化された場合も、参照先のデータは先に flush 済みです。項目が途中までしか書けなければ、チェックサムで無効になり、もう一方の世代を使います。CRC は偶発的な破損を検出するためのものです。任意の悪意ある改変を保証するものではありません。

スロットの更新で参照が消えた範囲は、次回の計画で再利用できます。復旧用に1世代前のデータも保持します。このため、同じサイズのチャンクを繰り返し更新すると3か所を交代で使います。ファイルの縮小は行いません。

保証の前提は、完了した flush の内容が残ることです。また、書き込み範囲外のバイトが変更されないことです。任意のディスク破損や、両方のスロットの破損は対象外です。

## WASM と OPFS

既存の `wasm-server` に `storage_call(op, ptr, len)` を追加します。別の WASM の取得や初期化を増やさず、既存のメモリ転送を使えるためです。ゲームの状態には触れません。ServerCore の ABI と台本の結果も変えません。Durable Object も同じ WASM インスタンスの圧縮処理を使います。

`shared/region-codec.ts` はバイト列を転送します。`opfs-store.ts` は OPFS の I/O を担当します。ワーカーは同じ WASM インスタンスを両方に渡します。WASM 呼び出しは同期です。出力は各呼び出し直後にコピーします。

操作0は保存済み番号の一覧です。操作1は読み取り位置と長さです。操作2は順序付きの書き込み計画です。入力はファイルサイズ u32、項目番号 u32、位置表49152バイト、保存するチャンクの順です。操作3はデータの展開です。この入力は圧縮されたセクタ範囲、またはゼロ埋めのないデータ部です。操作4は展開後のチャンクを入力し、セクタ境界のゼロ埋めなしのデータ部を返します。エラー時の戻り値は -1 です。出力の位置は既存の `server_out_ptr` で得ます。

ホストは `getSize` と `read({ at })` で位置表だけを読みます。一覧の作成ではデータを読みません。読み取りは Rust が指定した範囲だけです。書き込みは `write({ at })` と `flush` で計画に従います。短い read/write は残りを繰り返します。リージョンの処理はストア内で直列化します。処理後は必ずアクセスハンドルを閉じます。新しいファイルのデータを位置表より後ろに書くと、間の領域はゼロになります。

## Durable Object の保存

`chunks` テーブルの `data BLOB` は、`format INTEGER NOT NULL DEFAULT 0` で形式を区別します。0は圧縮なしの旧形式、1は圧縮形式です。コンストラクタで `PRAGMA table_info(chunks)` を確認し、列がない既存テーブルだけに `ALTER TABLE ... ADD COLUMN` を実行します。再起動しても列は重複追加しません。

保存時は常に操作4で圧縮し、`format = 1` で書き込みます。BLOB は圧縮データのバイト数 u32、圧縮方式 u8（1 = zlib）、展開後の CRC-32/IEEE u32、圧縮データの順です。整数はリトルエンディアンで、リージョンのデータ部と同じです。セクタ境界までのゼロ埋めは付けません。圧縮レベルと16 MiBの上限も共通です。

読み込みは `format = 0` ならそのまま、1なら操作3で展開してコアへ渡します。圧縮データの破損は座標を `console.warn` に出し、`chunkMissing` で再生成します。旧形式の行の一括変換は行いません。そのチャンクが次に保存されるときに圧縮形式に置き換えます。時計とチャンクは従来どおり同じ SQLite トランザクションで保存します。

## 旧形式の移行

ワールドを開いたとき、保存済み一覧を返す前に `c.<cx>.<cz>` を探します。リージョン側に有効なデータがあれば、展開と CRC 検証後にそちらを優先します。なければ旧ファイルを読み、通常の2段階保存を行います。両方の flush が終わった後に旧ファイルを削除します。

移行の途中で落ちた場合は旧ファイルが残ります。次回はデータのない項目だけを書き直します。保存後、削除前に落ちた場合はリージョンを優先して旧ファイルを削除します。削除が永続化されず旧ファイルが再び見えても、同じ手順で続行できます。読み取りや flush に失敗した場合は削除しません。エラーをワーカーの初期化失敗として返します。

## 検証と性能

Rust の単体テストは往復、上書き、セクタ再利用、圧縮、1024項目、位置表の各バイトの破損を検証します。メモリ上のファイルで各 write/flush の前後に強制終了を模します。さらに、各 write のすべてのバイト境界で途切れる場合も確認します。更新対象は古い値か新しい値を読めます。他の保存済みチャンクも読めます。初回保存の途中で落ちた場合の再開も検証します。

OPFS の模擬 I/O と実際の WASM を組み合わせたテストもあり、`pnpm build:wasm` のあとに `pnpm test:host` で実行します。移行の各 flush と旧ファイル削除の失敗、負の座標、リージョン優先、短い read/write、同時要求を検証します。

```sh
pnpm build:wasm
pnpm test:host
cargo run --quiet -p storage --example fixture > target/storage-fixture.bin
node tools/storage.mjs target/storage-fixture.bin
cargo test -p storage startup_ten_thousand_chunks -- --nocapture
```

起動の性能テストは実際の書き込み計画で1万チャンクのファイルを作ります。10リージョンに詰めた配置です。作成後に計測を始めます。ディレクトリの列挙、各ファイルのオープン、サイズ取得、位置表の読み取り、Rust での検証、保存済み一覧の作成を測ります。データ本体は読みません。ファイル作成直後なので OS のキャッシュが効く条件です。

2026年11月13日の Linux x86-64、Rust の debug ビルドでは **19.080 ms** でした。読み取る位置表は合計480 KiBです。テストは1秒未満であることを assert します。ブラウザの OPFS での計測はレビュー側で行います。

この環境では crates.io に接続できませんでした。検証時だけ、上流 GitHub の miniz_oxide 0.8.9 と adler2 2.0.1 のソースを `target/vendor` に置きました。Cargo の取得先は `target/cargo-home/config.toml` で切り替えました。これらは Git の管理対象外です。通常の依存宣言と Cargo.lock は crates.io を参照します。

`cargo test --workspace`、fmt、clippy、既存ホストテスト、クライアントの型チェックは通過しました。ネイティブと WASM の保存計画4136バイトも一致しました。シード2026、600 tick の台本は両方とも `05b4399b6948c67e` です。

`pnpm build` は WASM の生成まで成功しました。その後の Cloudflare/Vite のソケット作成が、実行環境の制限で `listen EPERM 127.0.0.1` になりました。`node tools/determinism.mjs` も子プロセスの結果取得が `spawnSync EPERM` になりました。ネイティブと WASM を個別に実行して、上記の一致を確認しました。dev と E2E は実行していません。

## エクスポートとインポート

シングルプレイの一時停止中の設定から、ワールドを1つの `.mcworld` ファイルに書き出し、別の名前で読み込めます。OPFS が使えない場合はエラーになります。書き出しは未保存の変更の保存を待ち、リージョン操作・メタデータ書き込みと同じキュー内でファイルを読み取ります。

形式は ASCII `MCWORLD`（7バイト）、版 u8（現在1）、項目数 u32、各項目の順です。項目は名前の UTF-8 バイト長 u16、名前、データ長 u32、データの CRC-32/IEEE u32、データで構成します。整数はすべてリトルエンディアンです。全体の CRC は付けません。全体は1 GiB、項目数は10万を上限とします。

名前は `meta.json` と `r.<rx>.<rz>`（座標は負数可の整数）だけです。重複や `meta.json` の欠落を拒否します。マジック・版・長さ・UTF-8・CRC・末尾の余分なデータを検証します。読み込みではさらにメタデータのシード・時刻と、RegionCodec の操作0による全リージョンの位置表検証を、書き込み前に行います。

現在のワールドや既存ディレクトリへの上書きは行いません。読み込み要求を直列化し、同名の読み込みはタブ間でも Web Locks で排他します。新規ディレクトリに全リージョンを書いて flush してから、最後に `meta.json` を書いて flush します。途中で I/O に失敗した場合は作りかけのディレクトリを削除します。ブラウザの強制終了では不完全なディレクトリが残る場合があり、その名前への再読み込みも上書き防止のため拒否します。
