# チャンクの圧縮保存

シングルプレイの OPFS と Durable Object の SQLite BLOB に使う形式です。形式と圧縮と書き込み計画は `crates/storage` が決めます。このクレートは I/O を行いません。HashMap と浮動小数点の超越関数は使いません。`meta.json` の形式と保存処理は変えません。

## ファイルと位置表

ファイル名は `r.<rx>.<rz>` です。1ファイルに32×32チャンクを入れます。`rx = floor(cx / 32)`、`rz = floor(cz / 32)` です。位置表の番号は `cz.rem_euclid(32) * 32 + cx.rem_euclid(32)` です。例えばチャンク `(-1, -33)` は `r.-1.-2` の番号1023です。

整数はすべてリトルエンディアンです。セクタは4096バイトです。先頭49152バイトを位置表に使います。1024個の項目があり、各項目は24バイトのスロットを2個持ちます。位置は `番号 * 48 + スロット番号 * 24` です。この初版では別のマジック値やファイルヘッダーを持ちません。

| スロット内の位置 | 内容 |
| --- | --- |
| 0 | 世代番号 u64。0は未使用です。 |
| 8 | データの開始セクタ番号 u32。12以上です。 |
| 12 | データのセクタ数 u32。0以外です。 |
| 16 | 先頭16バイトの CRC-32/IEEE u32です。 |
| 20 | CRC のビット反転値 u32です。 |

チェックサムと反転値を検証します。データがファイルの範囲に収まることも確認します。有効なスロットのうち、世代番号が大きい方を読みます。同じ世代なら後ろのスロットを選びます。通常の書き込みでは世代は重複しません。世代番号が上限に達した場合は書き込みを拒否します。

無効なスロットは無視します。両方とも無効なら未保存です。初回保存中の強制終了もこの扱いです。既存データの更新では、更新しない方の有効なスロットが残ります。短いファイルの位置表の不足部分は、ホストがゼロで補います。

データは次の順に並べます。圧縮データの後ろはセクタ境界までゼロで埋めます。

| 位置 | 内容 |
| --- | --- |
| 0 | 圧縮データのバイト数 u32です。 |
| 4 | 圧縮方式 u8です。1は zlib です。 |
| 5 | 展開後データの CRC-32/IEEE u32です。 |
| 9 | 圧縮データです。 |

圧縮は純 Rust の `miniz_oxide 0.8.9` の zlib、レベル6を使います。バージョンを固定します。SIMD 機能は有効にしません。ネイティブと WASM の書き込み計画全体を比較します。圧縮バイト列も一致します。展開後は CRC も確認します。1チャンクの展開後サイズは16 MiBまでです。リージョンの末尾は u32 のバイト位置の範囲に制限します。

## 書き込みと強制終了

Rust は順序付きの2個の書き込みを返します。各書き込みは位置とバイト列を持ちます。ホストは各書き込みの直後に flush します。

1. 両方の有効なスロットが参照する範囲を使用中とします。位置表の12セクタも保護します。
2. 最初に見つかる連続した空き範囲を選びます。空きが足りなければ末尾を使います。
3. 新しいデータを全量書いて flush します。
4. 現在選ばれていない方のスロットを、次の世代番号で書き換えます。初回は先頭のスロットです。
5. そのスロットを全量書いて flush します。この時点で保存完了です。

データの flush 前後に落ちても、以前の位置表とデータは変わりません。位置表の flush 前に新しい項目が永続化された場合も、参照先のデータは先に flush 済みです。項目が途中までしか書けなければ、チェックサムで無効になり、もう一方の世代を使います。CRC は偶発的な破損を検出するためのものです。任意の悪意ある改変を保証するものではありません。

スロットの更新で参照が消えた範囲は、次回の計画で再利用できます。復旧用に1世代前のデータも保持します。このため、同じサイズのチャンクを繰り返し更新すると3か所を交代で使います。ファイルの縮小は行いません。

保証の前提は、完了した flush の内容が残ることです。また、書き込み範囲外のバイトが変更されないことです。任意のディスク破損や、両方のスロットの破損は対象外です。

## WASM と OPFS

既存の `wasm-server` に `storage_call(op, ptr, len)` を追加します。別の WASM の取得や初期化を増やさず、既存のメモリ転送を使えるためです。ゲームの状態には触れません。ServerCore の ABI と台本の結果も変えません。Durable Object も同じ WASM インスタンスの圧縮処理を使います。

`shared/region-codec.ts` はバイト列を転送します。`opfs-store.ts` は OPFS の I/O を担当します。ワーカーは同じ WASM インスタンスを両方に渡します。WASM 呼び出しは同期です。出力は各呼び出し直後にコピーします。

操作0は保存済み番号の一覧です。操作1は読み取り位置と長さです。操作2は順序付きの書き込み計画です。入力はファイルサイズ u32、項目番号 u32、位置表49152バイト、保存するチャンクの順です。操作3はデータの展開です。この入力は圧縮されたセクタ範囲、またはゼロ埋めのないデータ部です。操作4は展開後のチャンクを入力し、セクタ境界のゼロ埋めなしのデータ部を返します。エラー時の戻り値は -1 です。出力の位置は既存の `server_out_ptr` で得ます。

ホストは `getSize` と `read({ at })` で位置表だけを読みます。一覧の作成ではデータを読みません。読み取りは Rust が指定した範囲だけです。書き込みは `write({ at })` と `flush` で計画に従います。短い read/write は残りを繰り返します。リージョンの処理はストア内で直列化します。処理後は必ずアクセスハンドルを閉じます。新しいファイルのデータを位置表より後ろに書くと、間の領域はゼロになります。

## Durable Object の保存

`chunks` テーブルの `data BLOB` は、`format INTEGER NOT NULL DEFAULT 0` で形式を区別します。0は圧縮なしの旧形式、1は圧縮形式です。コンストラクタで `PRAGMA table_info(chunks)` を確認し、列がない既存テーブルだけに `ALTER TABLE ... ADD COLUMN` を実行します。再起動しても列は重複追加しません。

保存時は常に操作4で圧縮し、`format = 1` で書き込みます。BLOB は圧縮データのバイト数 u32、圧縮方式 u8（1 = zlib）、展開後の CRC-32/IEEE u32、圧縮データの順です。整数はリトルエンディアンで、リージョンのデータ部と同じです。セクタ境界までのゼロ埋めは付けません。圧縮レベルと16 MiBの上限も共通です。

読み込みは `format = 0` ならそのまま、1なら操作3で展開してコアへ渡します。圧縮データの破損は座標を `console.warn` に出し、`chunkMissing` で再生成します。旧形式の行の一括変換は行いません。そのチャンクが次に保存されるときに圧縮形式に置き換えます。時計とチャンクは従来どおり同じ SQLite トランザクションで保存します。

コアから取り出したチャンクは、SQLite のトランザクションが成功するまで Durable Object のメモリに保持します。圧縮や書き込みに失敗したときはログに残し、次回の保存で再試行します。同じ座標の新しいデータがあれば上書きし、読み込み時は保存待ちのデータを SQLite より優先します。無人時は保存に成功してから tick を止めます。

`players` テーブルは `user_id` を主キーとし、最後に受理した足元の座標 `x`、`y`、`z`、`inventory` の BLOB、更新時刻 `saved_at`（ミリ秒）を持ちます。100 tick（約5秒）ごとの自動保存、無人時の停止前、デバッグ退避時に、接続中のプレイヤーと前回の保存後に切断したプレイヤーをチャンク・時計と同じトランザクションで保存します。座標とバイト列を前回の保存と比較し、変わった行だけを書き込みます。定期保存の目安は、動いているプレイヤー1人につき5秒に1行です。通常どおり自動保存できていれば、予告なしの再デプロイや退避で失われるのは、チャンクの編集と同じく直前の最大約5秒分です。

運用の接続（`ops:`）と認証なしの開発用の接続（`dev:`）は、接続のたびに識別子が変わるため保存しません。

現在のインベントリ形式（258バイト）には、所持品と選択枠に加えて、体力・空腹・酸素・死亡状態と死因も入ります。視線の向き、掘削の進み具合、開いていたインベントリ画面、落下や被ダメージの途中経過、疲労の蓄積、食事中や弓を引いている途中の状態は接続ごとに初期化します。

接続時はメモリの状態を優先し、なければ SQLite から読みます。保存行がない場合や座標が非有限値・数値以外の場合はスポーンから始めます。インベントリが欠けている場合や壊れている場合はゲームモードに応じた初期値を使います。BLOB が4 KiBを超える場合は保存時に警告を出し、位置を保存してインベントリ欄は NULL にします。参加取り消しやゲームモード変更でも行は引き継ぎます。

## 旧形式の移行

ワールドを開いたとき、保存済み一覧を返す前に `c.<cx>.<cz>` を探します。リージョン側に有効なデータがあれば、展開と CRC 検証後にそちらを優先します。なければ旧ファイルを読み、通常の2段階保存を行います。両方の flush が終わった後に旧ファイルを削除します。

移行の途中で落ちた場合は旧ファイルが残ります。次回はデータのない項目だけを書き直します。保存後、削除前に落ちた場合はリージョンを優先して旧ファイルを削除します。削除が永続化されず旧ファイルが再び見えても、同じ手順で続行できます。読み取りや flush に失敗した場合は削除しません。エラーをワーカーの初期化失敗として返します。

## 検証と性能

Rust の単体テストは往復、上書き、セクタ再利用、圧縮、1024項目、位置表の各バイトの破損を検証します。メモリ上のファイルで各 write/flush の前後に強制終了を模します。さらに、各 write のすべてのバイト境界で途切れる場合も確認します。更新対象は古い値か新しい値を読めます。他の保存済みチャンクも読めます。初回保存の途中で落ちた場合の再開も検証します。

OPFS の模擬 I/O と実際の WASM を組み合わせたテストもあり、`pnpm build:wasm` のあとに `pnpm test:host` で実行します。移行の各 flush と旧ファイル削除の失敗、負の座標、リージョン優先、短い read/write、同時要求を検証します。

```sh
pnpm build:wasm
pnpm test:host
cargo run --quiet -p storage --example fixture > target/storage-fixture.bin
node tools/storage.mjs target/storage-fixture.bin
cargo test -p storage startup_ten_thousand_chunks -- --nocapture
```

起動の性能テストは実際の書き込み計画で1万チャンクのファイルを作ります。10リージョンに詰めた配置です。作成後に計測を始めます。ディレクトリの列挙、各ファイルのオープン、サイズ取得、位置表の読み取り、Rust での検証、保存済み一覧の作成を測ります。データ本体は読みません。ファイル作成直後なので OS のキャッシュが効く条件です。

2026年11月13日の Linux x86-64、Rust の debug ビルドでは **19.080 ms** でした。読み取る位置表は合計480 KiBです。テストは1秒未満であることを assert します。ブラウザの OPFS での計測はレビュー側で行います。

この環境では crates.io に接続できませんでした。検証時だけ、上流 GitHub の miniz_oxide 0.8.9 と adler2 2.0.1 のソースを `target/vendor` に置きました。Cargo の取得先は `target/cargo-home/config.toml` で切り替えました。これらは Git の管理対象外です。通常の依存宣言と Cargo.lock は crates.io を参照します。

`cargo test --workspace`、fmt、clippy、既存ホストテスト、クライアントの型チェックは通過しました。ネイティブと WASM の保存計画4136バイトも一致しました。光源エンジン（#14）の追加後、シード2026、600 tick の台本はネイティブと Node（WASM）の両方で `88d6e0e1abd58ec4` です（更新理由・検証環境は [m0-report.md](m0-report.md)）。

`pnpm build` は WASM の生成まで成功しました。その後の Cloudflare/Vite のソケット作成が、実行環境の制限で `listen EPERM 127.0.0.1` になりました。`node tools/determinism.mjs` も子プロセスの結果取得が `spawnSync EPERM` になりました。ネイティブと WASM を個別に実行して、上記の一致を確認しました。dev と E2E は実行していません。

## エクスポートとインポート

シングルプレイの一時停止中の設定から、ワールドを1つの `.mcworld` ファイルに書き出し、別の名前で読み込めます。OPFS が使えない場合はエラーになります。書き出しは未保存の変更の保存を待ち、リージョン操作・メタデータ書き込みと同じキュー内でファイルを読み取ります。

形式は ASCII `MCWORLD`（7バイト）、版 u8（現在1）、項目数 u32、各項目の順です。項目は名前の UTF-8 バイト長 u16、名前、データ長 u32、データの CRC-32/IEEE u32、データで構成します。整数はすべてリトルエンディアンです。全体の CRC は付けません。全体は1 GiB、項目数は10万を上限とします。

名前は `meta.json` と `r.<rx>.<rz>` だけです。各リージョン番号は `0` または `-?[1-9]\d*` の正規の10進表記とし、`-0` や先頭の余分な `0` を拒否します。番号は `Number.isSafeInteger` の範囲内で、32倍してチャンク座標に戻し、`Math.floor(cx / 32)`（z軸も同様）で再生成した名前が元と一致する必要があります。OPFS 内のこの条件を満たさない名前のファイルは書き出し対象から除外します。重複や `meta.json` の欠落を拒否します。マジック・版・長さ・UTF-8・CRC・末尾の余分なデータを検証します。読み込みではさらにメタデータのシード・時刻と、RegionCodec の操作0による全リージョンの位置表検証を、書き込み前に行います。

現在のワールドや既存ディレクトリへの上書きは行いません。読み込み要求を直列化し、同名の読み込みはタブ間でも Web Locks で排他します。新規ディレクトリに全リージョンを書いて flush してから、最後に `meta.json` を書いて flush します。途中で I/O に失敗した場合は作りかけのディレクトリを削除します。ブラウザの強制終了では不完全なディレクトリが残る場合があり、その名前への再読み込みも上書き防止のため拒否します。

Web Locks がない環境ではタブ間の排他を保証できないため、OPFS の保存・読み込みを使わず、`persistence: off` で遊びます。ロックなしで初期化やインポートを実行すると例外になります。このアプリが必須とする WebGPU に対応したブラウザーには Web Locks もあるため、ロックなしの保存にはフォールバックしません。

## チャンク本体のかまど末尾

OPFSとDurable Objectに渡す展開前の論理データは、既存の `Chunk::to_bytes()` の直後に、simが次の末尾を追加する。圧縮コンテナーとは異なり、この末尾の整数は**ビッグエンディアン**（件数だけ既存のLEB128 VarInt）。クライアントへ送るChunkDataには追加しない。`Chunk::read` の厳密な末尾検証は変更せず、simでセクション群を走査して本体と末尾を分ける。

件数はu32 VarInt（最大16×16×384件）。u16では1チャンクの全ブロック数を表せないためVarIntを採用した。各項目はワールド座標の辞書順に並べる。以下の基本形式では 1 項目 25 バイトで、耐久値を含む形式は 31 バイトになる。 [耐久値の保存](#耐久値の保存)

| 項目 | 形式 |
| --- | --- |
| チャンク内x、ワールドy、チャンク内z | u8、i32、u8 |
| 入力、燃料、出力 | 各item u16 / count u8（空は0 / 0） |
| 燃焼残り、燃焼全体 | 各u32 |
| 精錬の進み | u16 |

末尾が全くない旧データは0件として扱う。かまどブロックのうち記載のない位置は空の状態にする。新しい保存は空のかまども含める。件数と長さ、x/zが0〜15、yが建築範囲内、実際にかまどブロックがあること、位置の重複、既知のアイテムと有効な個数を検証する。燃焼残りは全体以下、全体は0または登録燃料の時間、進みは160未満とする。不正ならチャンク全体を既存と同じ手順で破棄して再生成する。燃料枠・出力枠のアイテム種別は保存時には制限せず、クリックと精錬の規則で扱う。

保存後の読み込み解除でそのチャンクのかまど一覧も消す。読み込み解除中は精錬時間を進めず、次の読み込みから再開する。


## チャンク本体のスケジュール tick 末尾

かまどのデータに続けて件数を varint で書き、各件を x（u8）、y（i32 BE）、z（u8）、残り tick（u16 BE）の順で保存する。x と z はチャンク内の 0〜15、y は建築範囲内とする。残り tick は実行時刻から保存時の `game_time` を引いた値を 0〜65535 に収める。件数と残りバイト数は 1 件 8 バイトで一致する必要がある。

かまどの末尾までで終わる旧データと、末尾がまったくない旧データには予定がない。復元時は現在の `game_time` に残り tick を足す。同一時刻・同位置に復元された予定は 1 件にまとまる。チャンクの読み込み解除時にメモリ上の予定を取り除く。[スケジュール tick の実行](water.md#スケジュール-tick)

## チャンク本体のエンティティ末尾(⑧-1)

スケジュール tick の全項目に続けて、エンティティの件数を既存の LEB128 VarInt で書く。旧データがスケジュール tick の末尾以前の区切りで終わる場合は 0 件として読む。各項目は足元が属するチャンクに保存時の ID の昇順で入り、ID 自体は記録しない。以下の数値はビッグエンディアンで、浮動小数点数はビット列をそのまま読み書きする。

| タグ (u8) | 項目の順序 |
| --- | --- |
| 0 | 動物の種類 (u8、0 牛・1 豚・2 鶏・3 羊)、位置 x/y/z と速度 x/y/z (f64)、yaw (f32)、体力 (u8)、年齢 (u32)、接地 (u8、0/1)、産卵までの tick (u16、鶏は 1〜12000、ほかは 0) |
| 1 | アイテム ID (u16)、個数 (u8)、位置 x/y/z と速度 x/y/z (f64)、年齢と拾得待ち (u32)。消耗は 0 として読む。 |
| 2 | タグ 1 と同じ項目の末尾に、耐久値の消耗 `damage` (u16) が続く。 |
| 3 | 種類が羊のタグ 0 と同じ項目の末尾に、毛の色 (u8、白 0・灰 1・茶 2・黒 3) と毛が戻るまでの残り tick (u16、0〜2400) が続く。 |

タグ 0 の羊は白で毛のある状態として読む。タグ 3 の残り tick が 0 なら毛があり、1 以上なら刈られた状態とする。チャンクの読み込み解除中は残り tick が進まず、復元後に再開する。

位置は有限で、x/z はそのチャンク内、y は `health::VOID_Y` から建築範囲の上端（排他的な上限）+64 までとする。この高さの範囲外にいるエンティティは保存対象外とする。速度の各成分は絶対値が 8 ブロック/tick 以下、yaw は有限、体力は 1〜種類ごとの最大値、個数は 1〜登録済みアイテムのスタック上限とする。件数、項目の長さと値を検証し、不正値があればチャンク全体を既存の手順で再生成する。全項目を読み終えた位置からチェスト末尾を読む。

速度の上限 8 ブロック/tick は、空気中で落下する動物の終端速度（約 3.92）、落ちているアイテムの減衰後の終端速度（約 1.96）、最大まで引いた弓の矢の初速（3.0）より高く、衝突判定が走査するセル数を制限する。この上限を超える速度や有限でない速度のエンティティは書き出さない。読み込み解除済みのチャンクへ向かうアイテムは、その tick の水平移動を取り消す。

復元時は項目の順に `next_entity_id` から新しい ID を割り当てる。動物の歩き回りや逃走、無敵時間、環境ダメージの間隔は初期化し、落下開始高は復元した y にする。アイテムの接地は次の物理処理で更新する。出現は既存の同期で通知する。夜の敵と矢は一時的なエンティティとして扱う。クライアントの ChunkData にはこの末尾を含めない。

落ちているアイテムの生成・消滅・個数変化、動物の出現・死亡・消滅と、羊の刈り取り・毛の再生は、その tick で関係するチャンクを dirty にする。合体では両方のチャンクを、チャンク境界を越えた移動では移動元と移動先を dirty にする。これにより、シングルプレイで拾ったり捨てたりしたときに、チャンクと持ち物を次の自動保存で一緒に書き出す。復元で落ちているアイテムが全体で 1024 件を超えた場合は、生成時と同様に古い ID から取り除き、そのアイテムがいたチャンクを dirty にする。

同じチャンク内での移動、年齢や毛の再生待ち時間の進行などは、エンティティがいるチャンクに印を付け、600 tick ごとにまとめて dirty にする。ブロック更新などですでに dirty のチャンクも、`take_dirty` がその時点のエンティティを含めて書き出し、印を消す。読み込み解除の対象に印があれば直ちに dirty にし、`take_dirty` で書き出した後、まだ読み込み解除の範囲ならチャンクとエンティティをメモリから取り除く。

OPFS を開けなかったシングルプレイではエンティティの保存を無効にする。エンティティによる印や dirty は付けず、読み込み解除で動物とアイテムをメモリから取り除く。ブロック編集による dirty は従来どおり扱う。

OPFS のワーカーは書き出し・読み込み後の保存、タイトルへ戻るときの確認付き保存、ページ非表示・終了時の flush で、dirty なチャンクを集める前に印を反映する。Durable Object は無人時の停止前とデバッグによる退避時に印を反映する。両ホストの定期自動保存はシミュレーションが dirty にしたチャンクを集める。OPFS のリージョンと Durable Object の SQLite は、同じ論理バイト列を既存の方式で保存する。

## チャンク本体のチェスト末尾

エンティティの全項目に続けて、チャンク内のチェストの件数を LEB128 VarInt で書く。各項目は座標順で、x（u8）、y（i32 BE）、z（u8）、27枠の順に保存する。各枠は item（u16 BE）、count（u8）、damage（u16 BE）で、空枠はすべて0。枠は左上から行ごとの順で、1件は141バイトになる。

エンティティ末尾以前の区切りで終わる旧データではチェストは0件とする。記載のない位置のチェストは空として開ける。件数と残りバイト数の一致、x/zが0〜15、yが建築範囲内、同じ位置の重複がないこと、その位置にチェストブロックがあること、各枠が空か既知のアイテムと有効な個数を持つことを検証する。耐久値の読み込みはかまどの枠と同じ。余分なバイトや不正な項目があればチャンク全体を既存の手順で破棄して再生成する。

中身が変わるとチャンクをdirtyにする。読み込み解除時にそのチャンクのチェストをメモリから取り除き、再読み込み時に保存した内容を復元する。state_hashには読み込まれたチェストの件数と、座標順の位置および27枠の全内容を含める。クライアントのChunkDataにはこの末尾を含めない。

## BFCache とシングルプレイのワーカー

同じタブで別の URL へ移ると、ブラウザは前のページを戻る/進むキャッシュ（BFCache）に入れることがある。`pagehide` の `event.persisted` が true のときがそれである。シングルプレイの sim worker が OPFS のファイルを `createSyncAccessHandle` で持ったまま凍結されると、新しいページが同じワールドのファイルを開いたときに Chrome が旧ページを BFCache から追い出す。この追い出しで旧 worker のスレッドが落ち、同じレンダラーで動いている新しいページも一緒に落ちることがある。

BFCache に入るシングルプレイでは、sim worker を `close()`（`Worker.terminate()`）で止める。止める前に保存の `flush()` を投げてよい。BFCache に入るときに始めた flush は完了しないので、worker を止めても、完了まで届く保存は増減しない。BFCache から戻ったとき（`pageshow` の `persisted` が true）は worker が止まっているので、`location.reload()` でページを作り直す。

ページが実際に破棄される `pagehide`（`persisted` が false）では `flush()` だけを行う。マルチプレイもローカルの sim worker を持たないので、`pagehide` は `flush()`、BFCache から戻ったときは `resume()` である。`visibilitychange` で hidden になったときの `flush()` も同じである。

Chrome では `Worker.terminate()` が親ワーカーのコンテキストを破棄し、その破棄を購読している子の dedicated worker も terminate する。親スレッドは子が止まるまで終了を完了しない。地形生成の gen worker は sim worker から作られるので、ここで一緒に止まる。gen worker は OPFS を開かない。sync access handle を持っているのは sim worker である。

シングルプレイの自動保存は、未保存のチャンクがあるとき、前回の保存開始から20 tick（約1秒）経過すると実行する。チャンクに変更がなくても100 tick（約5秒）でプレイヤー状態と時刻を保存する。保存中に自動保存の間隔が過ぎた場合は、書き込みが終わった後の tick で再判定する。

OPFS を開けず `persistence: off` で動くワールドは、BFCache に入る際もワーカーを維持する。復帰時にページをリロードするのは、BFCache に入る際にワーカーを止めた場合だけである。

## 耐久値の保存

OPFS の `player.dat` と Durable Object の `players.inventory` は同じプレイヤーデータを使う。版 6 は 258 バイトで、版番号と選択枠 (各 u8)、所持品 36 枠・2×2 クラフト 4 枠・カーソル・作業台 9 枠の順に各枠のアイテム ID (u16)、個数 (u8)、`damage` (u16)、最後に版 5 と同じ体力・空気・死亡フラグ・死因・満腹度の 6 バイトを記録する。空枠の 3 項目は 0。版 1〜5 の枠は `damage = 0` で読み込む。

落ちているアイテムは、消耗していればチャンク末尾にタグ 2 のレコードで保存する。消耗の無いアイテムと旧レコードはタグ 1 を使う。かまどに消耗した道具が入っているチャンクでは、かまどの件数を表す VarInt の最上位ビット（ビット 31）を立て、各かまどの各枠の個数に続けて `damage` (u16) を書く。フラグの無い保存では、かまどの各枠の `damage` は 0 になる。

読み込み時に、`damage` が最大耐久値以上なら最大値より 1 少ない値に切り詰める。耐久値を持たないアイテムの `damage` は 0 に戻す。
