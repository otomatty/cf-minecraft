# 光源エンジン（issue #14、Rust 中核）

## 計算とデータの所有

`world::light` は I/O のない整数演算の実装で、サーバーの `sim` と
`wasm-client` のワールドの鏡が同じコードを使う。光はブロック配置と読込済み
チャンク集合から決定論的に導けるため、ネットワーク送信も保存もしない。
生成・保存からの読込・クライアント受信は `World::insert_chunk` に集約する。
`World::new()` / `Default` は照明が無効で、挿入・編集・撤去では光を計算しない。
`World::with_lighting(true)` で有効にした場合だけ、その場で初期計算する。
`Chunk::read` 単独では照明は未計算。
`Chunk::write` / `to_bytes` とパケット形式は従来どおりブロックのみ。

`Chunk::lighting: Option<Box<ChunkLighting>>` に光配列と高さマップをまとめ、
無効時は `None` とし、どちらのデータも確保しない。既に照明のあるチャンクを
無効な World に挿入した場合も、その照明データを破棄する。
有効時の各セクションは、スカイライトとブロックライトをそれぞれ
2048 バイトのニブル配列に持つ。インデックスは `(y << 8) | (z << 4) | x`、
偶数インデックスが下位4ビット。均一な配列は値だけを保持し、書換時に展開する。
初期計算の終了時には均一な配列を再圧縮する。
高さマップはチャンク内 `z * 16 + x` 順の256列で、opacity が正の最も高い
ブロックの直上の Y。遮蔽物のない列は `MIN_Y`、最上部が塞がった列は320。
`occludes` は面の遮蔽・AO・光採取の除外用で、光の属性とは独立している。
独自の `lamp_block` は全面不透明で opacity=15、emission=15、テクスチャも
コードで描く独自の枠・菱形模様。

## 公開規則と式

出典: [Minecraft Wiki: Light — Block light / Sky light](https://minecraft.wiki/w/Light)
（2026-11-14 確認）。逆コンパイルしたコードは使用していない。
方向別の遮蔽は対象外。ガラス・葉・水、およびハーフブロック・草花の扱いは末尾を参照。

隣接セル `p → q` に対し、移動先の opacity を `o(q)`、発光を `e(q)` とする。
ブロックライトは `max(e(q), max_p max(0, B(p) - max(1, o(q))))`。
ただし opacity=15 には外から入射せず、そのセル自身の発光だけを持つ。

スカイライトは空に直結した列で15。伝播量 `T(p,q)` は、移動先が opacity=15
なら0、`S(p)=15` かつ真下への移動かつ `o(q)=0` なら15、それ以外は
`max(0, S(p) - max(1, o(q)))`。セルの値は直射光と各隣接セルからの伝播量の最大値。

**仕様の解釈:** タスク中の「真下へは減衰せず」は、公開規則と本家一致の条件に
合わせてレベル15の直射光に適用する。横から回り込んだ14以下の光は下方向にも
1ずつ減る。閉じた縦穴のテストで10→9→…→1を確認する。
昼夜によって保存するスカイライト値は変えず、時刻の見た目の係数は描画側で扱う。

## 初期計算・増減・境界

初期計算は高さマップから直射光を設定し、遮光された通光セルの周囲と
読込済みの隣接チャンクの境界をキューに入れ、幅優先で増加を伝播する。
発光セルを種とするブロックライトも同様。後から隣が届けば両側の光を伝え合う。
未読込のチャンクは閉じた境界で、空や光源とはみなさない。

ブロック変更時にはその列の高さを更新する。旧値に依存し得る光を BFS で0にし、
影響域の発光・直射光と、外周に残った光を種として別の BFS で伝え直す。
この二段階を分けることで、撤去した光源の光や循環した古い光が残らない。
opacity / emission が変わらない編集では光の更新は不要。
`remove_chunk` でも外周からの依存光を消して再伝播する。
光の更新は周囲のチャンクを保存用 dirty にはしない。

キューは `VecDeque`、チャンクは `BTreeMap`。方向は下・上・北・南・西・東の固定順。
初期走査・境界走査も固定順で、浮動小数点も `HashMap` も使わない。
`Chunk::hash_into` は照明が存在する場合、全セクションの sky / block の論理的ニブル列と高さマップを含む。
通常の `World::hash_into` は照明が無効な場合、ブロックだけをハッシュに含める。
均一表現か展開済みかに依存しないため、編集履歴やチャンクの到着順でも同じ値になる。

読込済みワールドの変更は `World::set_block` / `insert_chunk` / `remove_chunk` を使う。
生成中の未挿入チャンクは従来どおり `Chunk::set` で組み立てられる。
`World::set_lighting_enabled(true)` は既存の全チャンクを再計算して有効化し、
`false` は光配列と高さマップを解放する。同じ設定値への変更は何もしない。
`World::rebuild_light` は明示的に照明を有効にし、読込済みの全チャンクをブロックから再計算する。
`sky_light` / `block_light` は無効時には0を返す。

## サーバーとクライアントでの有効化

`sim` は照明を無効にし、`wasm-client` の鏡だけ有効にする。
現在のサーバーは光をゲームロジックに使っておらず、参加時の大量のチャンク計算を
通常の tick に載せる必要がない。クライアントはメインスレッドのフレーム予算で初期照明を計算する。

修正前にユーザーが workerd に対して実施した
`node tools/tick-probe.mjs --players 8 --seconds 30 --view 8` の計測:

| 条件 | TPS | 落ちた tick | タイマー間隔 p99 |
|---|---:|---:|---:|
| main | 20.0 | 0 | 59ms |
| 光を常時計算する修正前の実装 | 13.6 | 193 | 1,681ms |

修正前の読込チャンク数は2,567。WASM ではネイティブより計算が重く、参加時に
tick を圧迫していた。今回、開発サーバーは起動しておらず、修正後の workerd の
TPS は未計測。通常の tick で照明を確保・計算しないことは Rust テストで検証する。

決定論の `sim::scenario` は、通常の無効なワールドで台本を進めた後、最後の
ハッシュ取得直前に `rebuild_light` を一度呼ぶ。これにより光の計算結果も
ネイティブ・Node・workerd で比較できる。実運用の tick には影響しない。
今回実行した比較ホストはネイティブと Node。

## クライアント用 API

`client_padded_light(cx, sy, cz)` はセクションの1ブロック外周を含む18³個をコピーし、
要素数5832を返す。`client_padded_sky_ptr()` と `client_padded_block_ptr()` は
各1バイトのレベル配列で、既存の `mesher::padded_index` と同じ順序。
照明が無効なら0を返し、パディング済みの光配列も確保しない。
有効時には空気だけのセクションも取得可能で、初めて取得するときにバッファを確保する。
範囲外のセクション・未読込の中心チャンクは0を返す。
下限より下と未読込の周囲は0、上限より上のスカイライトは15。
配列は次の取得呼出しまたはクライアント初期化まで有効。
メッシャーと Worker は、この配列を使って頂点の光を計算する。

## 検証と性能

Rust テストは平地・閉じた地下・屋根の横からの減衰・閉じた縦穴・
光源1個のトンネル・複数光源・設置破壊・境界越え・遅延読込・置換・撤去を検証する。
固定シードの120編集では40編集ごとに逆順挿入による全再計算と全セル・高さ・ハッシュを比較。
保存データからの再計算と、照明を明示的に有効にした鏡の18³配列も検証する。
既定で光データを持たないこと、有効化・無効化・再有効化、照明によるハッシュの差、
無効な鏡の API が0を返してバッファも確保しないことを検証する。

再現コマンド:

```sh
cargo test --release -p world lighting_timings -- --nocapture
```

2026-11-14、この作業環境（x86-64、Rust 1.99.1、release、単発測定）では、
照明有効時の平地1チャンク（Y=-64..0が石、上が空気）の初期計算が **0.249ms**、
その地表に光源1個を設置する増分更新が **0.163ms**。
無効時の同じチャンクの挿入は **0.127µs**、光源設置は **0.130µs**（照明計算なし）。
初期計算では、均一な通光セクションを高さ検索から飛ばし、均一な非発光セクションを
光源検索から飛ばす。完全遮光・全面直射光のセクションは BFS の種の検索から除外し、
未読込の境界もセル単位ではなく辺ごとに一度だけ判定する。
修正前の初期計算は0.575msで、今回の測定では0.249msとなった。
チャンクのブロック組立・シリアライズは初期計算の計測外。
変更の計測には高さ更新と sky / block 両方の更新を含む。
共有マシンでの参考値であり、時間をテストの合否条件にはしていない。

決定論の新しい台本ハッシュとホスト検証結果は [m0-report.md](m0-report.md) に記録する。


## クライアントのスレッド分担と invalidation（issue #14、第2 PR）

通常時、メインの WASM World は「外から光を受け取る」モードで、初期計算も
編集時の増分計算も実行しない。ブロック受信・予測・raycast・衝突は従来どおり
メイン側で即座に反映する。`ClientCore.observeLight` から、有効な ChunkData /
UnloadChunk / BlockUpdate の生バイト、成功した予測編集、reset を同じ順序で
`light.worker.ts` へ送る。Worker は独立した client.wasm と World を持つ。
Welcome / TimeUpdate はブロック・光に影響しないので送らない。

Worker 内では `insert_chunk_unlit` がブロックを保存し、`client_light_step` が
水平距離でカメラに近いチャンクを初期化する。カメラはメインから100 msごとに通知。
2 ms の処理スライスごとに `setTimeout(0)` でメッセージループに戻るので、
初回計算は描画 FPS に依存せず進み、編集・アンロードもスライス間に処理できる。
チャンク1個は不可分なので、その1個ぶん期限を超えることはある。
編集は Worker 側で既存の増減 BFS をその場で実行する。

`take_light_changes` の記録はクライアントだけ opt-in する。
Worker は記録したセクションをまとめて返す。1レコードは cx / sy / cz /
世代の4個の LE u32 と、sky 2048バイト・block 2048バイトのニブル配列で4112バイト。
メッセージ1個の全レコードを1つの ArrayBuffer に詰めて Transferable にする。
受信側は均一なニブル列を Uniform に戻す。高さマップはメインでは使わず転送しない。

世代番号はメイン側が ChunkData ごとに単調増加させ、reset 後も再利用しない。
メインと Worker の WASM に同じ番号を設定する。TS と Rust の両方で、現在読込済みの
チャンクと世代が一致するレコードだけ適用する。アンロード済みの光、アンロード→
再読込の古い光、reset 前の光は破棄する。24セクションすべてを受信して初めて
そのチャンクの初期照明が完了する。dirty 選択は中心と周囲8チャンクの完了を待つ。

受信・増分更新では、光が変わったセクションと3×3×3周囲の非空セクションを
保守的に dirty にする。ブロック変更自体は空になったセクションも dirty にする。
編集直後は古い光で一度メッシュ化してよく、最新の光が来れば再び dirty になる。

`lightQueue` は Worker が最後に報告した待ちチャンク数と、送信した変更のうち
未適用・未応答の数の和。応答の光をすべて適用してから通番を acknowledge するため、
メインに結果が届く前に0にならない。`lightMs` はフレーム間の受信・世代判定・
WASMへの書込に使ったメインスレッドの時間。`lightFallback` でフォールバックを確認できる。

Worker 作成不可、起動10秒タイムアウト、実行・メッセージエラーでは Worker を終了し、
メイン World の光を破棄して全チャンクを未計算に戻す。既存ブロックをそのまま使い、
従来の `LIGHT_FRAME_BUDGET_MS = 2` のフレーム予算で再計算する。
この経路だけメインで初回・増分計算を行い、`lightQueue` はメインの未計算数、
`lightMs` は予算処理の時間になる。起動直後に届いた変更は ready まで順序付きで保留し、
ready 後に送信する。

## 遅延経路とパディングの性能確認

再現コマンド: `cargo run --release -p worldgen --example light_bench`。
DebugHills、seed 2026、半径12の625チャンクを事前生成し、通常挿入と全受信後の
近距離順の遅延照明の合計・最大・比率を出す。生成とクローンは計測外。
遅延側は未点灯挿入の時間も含む。最後に両経路の全セルの論理値を比較する。

原因は境界交換が `chunks.contains_key` だけで隣接チャンクを判定していたこと。
未点灯チャンクにも毎回高さ384×幅16×sky/block×双方向の走査を行い、
伝播先として閉じているセルへ送る不要なキューも作っていた。
照明がある隣接チャンクだけを境界交換の対象にした単独の変更で、同一環境の
release 実行は通常1.455秒 / 遅延3.786秒（2.602倍）から、
通常1.433秒 / 遅延1.471秒（1.026倍）になった。配列圧縮の変更は不要だった。
時間は共有マシンの参考値であり、通常のテストには時間の閾値を入れない。

`paddedLight` は同じ WASM セクションを100回ウォームアップ後、2000回取得する
Node の小テストで、変更前約183 ms、変更後約37 ms。
従来は各セルで sky/block 別々に BTreeMap を検索していた。今は周囲9チャンクの
光を一度取得し、ニブルを直接読む。sky と block は連続した1つの WASM バッファに
書き、JS でも1回の slice の2つの subarray にする。MeshPool は共有 ArrayBuffer を
重複せず transfer する。描画全体と view=12 の性能・E2E はレビュー側で測定する。

## 頂点のスムーズライティング

各頂点で面の外側の接する4セルを取り、完全不透明セルを除いて sky / block を
別々に平均する。整数への丸めは `(sum + count / 2) / count`。
可視面の直外のセルは必ず非不透明なので count は1以上。
光配列が省略されたメッシュ単体 API は sky=15、block=0 の昼光を使う。
既存の方向シェードと AO は維持し、光とは独立して乗算する。
word 1 は `texture:12 | tint:1 | sky:4 | block:4`（下位から）。
`client_mesh` と Worker の `mesh_padded` は同じメッシャーを通す。
Worker にブロックと2種類の光のスナップショットを Transferable として渡す。

参考: [Overviewer の公開実装と説明](https://docs.overviewer.org/_/downloads/en/latest/pdf/)
の頂点周囲のサンプリング、および
[Minecraft Wiki: Light](https://minecraft.wiki/w/Light) の smooth lighting / lightmap の説明。
逆コンパイルしたソースは使用しない。

## 16×16 ライトマップの式

横軸 B=block、縦軸 S=sky。`sky.ts` の `lightmap` が RGBA8 を計算し、
毎フレーム GPU テクスチャに転送する。頂点では `(B+0.5, S+0.5)/16` を渡し、
面上で補間した座標から線形サンプリングする。
空・雲・太陽・月のシェーダーは変更しない。

公開されているライトマップの考え方（sky と block の2軸、昼夜で sky のみを弱める、
暖色の block、非線形の明度）に基づく独自の近似式で、本家との画素単位一致は狙わない。
レベル L に対して `q(L) = (L/15) / (4 - 3L/15)`。
空の寄与は `s = q(S) * sky.skylight`。既存の空の時計から得る
`sky.skylight = 0.18 + 0.82 * clamp(2 * sunHeight + 0.2)` を使うので、月夜の空光は残るが
閉じた地下の S=0 には影響しない。
各色のブロック寄与は `b = q(B) * (1, 0.85, 0.65)`。
混合は色ごとに `m = max(s,b) + 0.15 * min(s,b)`、
最終色は `0.04 + 0.96 * clamp(m)` として最低明度4%を確保する。
昼の S=15/B=0 は白、S=0/B=0 は昼夜とも最低明度、B=15 は夜でも暖色で明るい。
このライトマップ色にテクスチャ色・方向シェード・AO を乗算し、従来どおり fog を適用する。
地形全体に掛けていた時刻の係数は廃止した。

検証: Rust で平均・不透明セル除外・パディング経由との一致、初期計算の段階実行と
再計算との一致、境界越えの増分 invalidation を確認する。node:test でフレーム予算、
ライトマップと Worker の3配列転送を検証する。
`tools/e2e.mjs` に密閉地下室の暗さとランプ設置後の明るさの画素比較を追加した。
E2E・描画性能計測はレビュー側で実行する。


## ガラス・葉・水（issue #16、第1 PR）

公開出典（2026-11-15確認）:
[Minecraft Wiki: Opacity](https://minecraft.wiki/w/Opacity)、
[Minecraft Wiki: Light — Sky light / Block light](https://minecraft.wiki/w/Light)。
逆コンパイルしたコードは参照していない。Java Edition の説明を対象とする。

ガラスは光を遮らず、葉と水はスカイライトを1段階ずつ弱めるという説明に基づき、
このレジストリの opacity は glass=0、oak_leaves=1、water=1、いずれも emission=0 とした。
ガラスを通るレベル15の直射光は真下へ15のまま伝わる。
葉・水の縦列は15→14→13と減る。横方向や拡散した光はガラスでも通常の距離減衰を受ける。
ブロックライトにも元から各セル最低1の距離減衰があるので、葉・水の opacity=1 は
追加の距離減衰を与えない。opacity と見た目の alpha、衝突、AO は独立している。
葉・水・ガラスは occludes=false なので、AO を落とさず頂点の光採取からも除外しない。
面の遮蔽規則とサンプリングの扱いは [render-layers.md](render-layers.md) を参照。

## ハーフブロック・草花（issue #16、第2 PR）

`oak_slab` / `cobblestone_slab` の bottom・top は opacity=0、double は15。
red_flower / yellow_flower / short_grass は0で、いずれも emission=0。
bottom・top・草花はセル単位では光を通し、レベル15の直射スカイライトを真下へ15のまま伝える。
横方向・拡散光とブロックライトの最低1段の距離減衰は従来どおり。
double は完全な立方体と同じく入射光を遮る。

本家の方向別・形状別の遮り（例えば下付きハーフが下からの光だけを遮る挙動）は再現しない。
形の占有率で減衰を調整する処理もなく、bottom と top の光の計算は同一である。
`occludes=false` の部分形状と草花は AO の遮蔽物にも、光サンプリングの除外対象にもならない。

セル境界上の面は従来どおり、外側の最大4セルから光を平均し、AO を計算する。
下付きの上面・上付きの下面など内部面は、面のすぐ外側も同じセルにあるため、
自セルの光を採取する。Cross も自セルの値を全頂点に使う。
内部面と Cross の AO は最大（3）。光の値そのものを最大にするわけではなく、暗い場所では暗い。
Cross の方向シェードは1.0。部分形状の詳細と頂点 ABI は [render-layers.md](render-layers.md) を参照。

## サーバーでの局所的なブロックライト(⑦-4a)

サーバーはチャンク全体の照明を無効にしたまま、夜の敵の出現候補が地形・距離の
条件を満たしたときに `World::local_block_light` で足元の空気セルを調べる。
光配列、高さマップ、状態ハッシュには書き込まない。

発光は最大15で、ブロックライトは1ステップごとに最低1減衰する。
対象に正の光量を届ける経路は14ステップ以下なので、経路上のセルはすべて
対象からマンハッタン距離14以内にある。その範囲を固定順で走査し、
発光セルから幅優先で伝播する。残りの距離を進むと光量が0になる経路は
打ち切る。減衰は全体の照明と共通で、未読込チャンクとワールドの高さ範囲外への
伝播は止める。照明有効時に初期照明を遅延しているチャンクも準備が済むまでは
閉じた境界として扱う。計算には29³セル分の固定長配列2つとキューを使い、
対象に届き得る光源がなければキューのヒープ確保は発生しない。

```sh
cargo test --release -p world local_block_light_timings -- --nocapture
```

2026-11-20、x86-64（Intel Xeon 2.10 GHz、Rust 1.99.1、release）で、
照明無効の平地3×3チャンク（Y=-64..0が石、上が空気）の中央付近を1,000回ずつ計測した。
1回の平均は、光源なしで **30.7 µs**、5ブロック先にランプ1個（対象の光量10）で
**34.3 µs**。チャンクの組立とランプの設置は計測外。

## たいまつ（⑦-4b）

床の `torch` と壁の `wall_torch` はどちらも emission=14、opacity=0。
設置・撤去は既存のブロック更新を通じてクライアントの照明計算に伝わり、周囲のブロックライトを増減させる。
局所ブロックライトが1以上のセルを除外する敵の出現判定（PR #105）にも、この光源が効く。
